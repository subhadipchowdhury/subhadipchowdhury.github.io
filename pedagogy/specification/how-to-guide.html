A companion to the Teaching Matters column “Teaching Your AI How You Teach.”

Subhadip Chowdhury, Department of Mathematics

The column argued that an AI model already has the content knowledge a course needs and lacks your knowledge of how to teach that content. Shulman called that pedagogical content knowledge, and it stays tacit until you write it down. A teaching specification is what you write down, in enough detail that a model can follow it. This guide is about writing it and keeping it current over a quarter.

In my current setup the specification is no longer a single document. It is a set of markdown files, plain text with a few formatting marks, in the folder where the course lives on my own computer. Claude reads each kind at a different time. Each conversation with Claude is a separate session, and a new session starts with no record of earlier ones except what is written in these files. There are working notes it reads at the start of every session, short notes it writes each time I correct it, instructions for the jobs I repeat every week, and longer documents it opens when a job needs them. I can open any of these files, read what Claude has recorded, and change it.

Claude Code, Anthropic’s AI assistant for working with files, works inside that folder from VS Code, Microsoft’s free editor. I now work there rather than in the Claude chat in a browser or the desktop app, mainly because I can watch it work. Its panel shows every file it opens, every command it runs and its output, and every edit it makes, with its reasoning between the steps. When a draft goes wrong, I can see which files it read and what it assumed.

The examples come from my Autumn 2026 Numerical Analysis course. The guide assumes no prior experience with these tools, though you will be installing an editor.

This page was drafted with Claude and revised by me before posting.

Step 1

Keep the course in one folder

Put everything for one course in one folder, since Claude Code works on the files in the folder you open. Mine holds the lecture notes and their LaTeX sources, the homework and the assessments, the syllabus, the schedule and the standards, the textbooks and old notes I draw on, and the documents that make up the specification.

Keep it somewhere with version history, such as OneDrive or Box. Claude edits files in place, and with version history you can recover a file it rewrote badly. Because the folder syncs, you also have the same files on every computer you work from.

Step 2

Install Claude Code and open the folder

  1. Install VS Code, a free editor from Microsoft, from code.visualstudio.com.
  2. In VS Code, open the Extensions view from the Activity Bar on the left, search for Claude Code, install it, and sign in with your Claude account.
  3. Open the course folder with File > Open Folder, then open the Claude panel.

Claude can now read, search and edit the files in that folder, and run commands on your computer, such as a Python script or the LaTeX compiler. By default it asks before it edits a file or runs a command. Keep that setting until you have seen how it works.

Because Claude works on your files directly, it can check a computation by writing a short Python script and running it, and it can compile a document written in LaTeX, a typesetting system, into a PDF and look at the pages that come out. Claude also writes a correction straight into the document, without a copy for you to download, edit and upload again.

VS Code is a programmer’s tool, so it will look unfamiliar if you have not used an editor before. The file list on the left and the Claude panel are all you need.

What stays on your computer

Claude Code, the files it edits and the commands it runs are all on your computer. The language model behind Claude runs on Anthropic’s servers. Anything Claude reads, a file included, is sent there as part of the conversation. Under a commercial account, which includes the University’s Claude Enterprise plan, Anthropic does not train its models on that data unless the institution opts in. Check the University’s rules on student data before Claude reads any student work.

Nothing you do changes the model itself. Every new session starts with the same model and no record of your earlier sessions beyond the files in your folder. Over the quarter the text in those files grows, and Claude reads what it needs from them in each new session. You can therefore read everything it has recorded about your course, and correct it.

Step 3

Write down how you teach

Start with one kind of material in one course, such as worksheets, problem sets, exam questions or lab handouts, and add the other kinds later. Writing down how you teach in general is too large a first job.

Collect a dozen or so pieces of that material that you have already made and would hand out again. Hold two or three of them back for the test in Step 4, since that test needs work the model hasn’t seen. Pick the remaining eight to ten for range, from different weeks and topics, with the short ones alongside the long ones. Claude infers a rule from what stays the same across pieces that otherwise differ, so ten varied pieces show it more of your rules than thirty similar ones. Add two or three pieces you were unhappy with. For each of these you can usually say what went wrong, and that gives Claude a rule about what to avoid.

The files are already in the folder, so list them for Claude instead of uploading them.

Paste into the Claude panel

Read the files listed below. I want a specification document detailed enough that you could write a new piece in my style by following it. Infer the design rules I appear to be using, covering structure, sequencing, difficulty, voice, how much I explain versus how much I ask, and anything I consistently avoid. The files marked as rejects are ones I was unhappy with; say what distinguishes them from the rest. Write the result to [course]_specification.md as a numbered list of rules. For each rule, cite the file you drew it from, and mark anything you are guessing at. [list the files, marking the rejects]

Some of the rules in Claude’s first draft will be right, some will be wrong, and many will be missing. Correcting a rule it has written down is still quicker than writing the rule yourself. Then read the draft yourself three times, each time looking for something different.

First, check each rule against your material. From only ten pieces, Claude may mistake coincidences for rules. It might report that you always open with a figure when seven of the ten happen to, or turn a constraint from one unit, such as the quarter you taught in a room with no projector, into a standing rule. Delete the rules that are wrong and correct the ones that are half right.

Second, sharpen whatever is still vague. Keep a rule only if a colleague, reading a draft, could tell you whether it had been followed.

Too vague Keep the worksheet engaging and appropriately challenging.
Usable Exposition takes about 30 percent of the page and questions the rest. The hardest part of a question takes no more than five to seven minutes of focused work in class.
Too vague Do not give too much away.
Usable No sentence after an in-class question states what the question was meant to find. The tool a question needs, such as a theorem or a formula, never appears in the sentences just before it.
Too vague Use an appropriate academic tone.
Usable No em dashes or en dashes. “We” in the exposition, and “you” only for instructions at the keyboard, the reader’s own earlier work, and requests for the reader’s judgment.

Third, add what Claude could not have found in your material. The pieces you were unhappy with show only the failures you kept. They do not show drafts you abandoned, topics you refuse to assign, or framings you never use. Ask yourself what makes you throw material away, and write those answers down.

Stop there, even though the document is short. Most rules come later, from cases you haven’t met yet, and Steps 8 and 9 describe how to collect them.

What to write down

Nearly everything worth writing down falls under six headings. Don’t try to write all six today.

  1. Purpose and audience. What the material is for, who the students are, what they have already seen, and how they will be assessed.
  2. Design principles with their reasons. Why a question comes before the theorem it leads to, why a proof becomes an exercise with blanks, why a question uses a particular function only when its answer needs one. A model can extend a rule to a case you didn’t anticipate only if it knows why the rule is there.
  3. Rejection triggers, the things that make you throw a draft away, from your third reading. Left to itself, Claude writes material that reads like a standard textbook, so much of what you write down is what to reject.
  4. Voice and prose. Banned words and constructions, register, how you address students, and formatting habits.
  5. Format conventions. Section structure, numbering, length limits, the ratio of exposition to student work, and any typesetting or template details.
  6. An example of what you do write. A piece of material you consider correct, with notes on what each part is doing and why it sits there. This can be one of the pieces you held back, once you’ve finished testing with it.

Give the sixth heading as much care as the third. A list of bans tells Claude only what to remove, and prose written from it comes out flat. For prose I now keep a separate description of how I write lecture notes. It cites passages from my own notes to show how a section motivates its reader, how the mathematics is made clear, and what reads as talking down to students.

Step 4

Test it before you trust it

Ask Claude to produce one of the pieces you held back, then compare its version with yours. Wherever the output diverges from what you would have written, work out which of three things happened. The document does not cover that point, or it says the wrong thing, or it is right and Claude did not follow it. The first two you fix by editing the document. For the third, restate that one rule as a prohibition, which a model follows more reliably than a preference. In two or three of these tests I found most of what was missing from mine.

This test is about style, and whether the content is correct is the subject of Step 11.

Step 5

Decide where each rule lives

Claude does not read every file in the folder in every session. It reads a few files at the start of each session, and opens the rest when a job needs them or your prompt names them.

CLAUDE.mdHow to work in this folder, which document governs what, the order of work, and rules that hold for every jobIn full, at the start of every session
MEMORY.md, the index of memory notesOne line for each memory noteAt the start of every session, up to its first 200 lines or 25 KB, whichever limit it reaches first
Memory notesOne correction or decision each, with its reasonWhen a job needs it
SkillsThe steps of one routine jobIts description in every session, and the full steps when the job starts
Longer documents, such as the specification from Step 3, a description of your voice, the schedule and the standardsWhat one kind of work needsWhen a job needs them or your prompt names them

Put each rule in a file that Claude reads when the rule applies. A rule for every job goes in CLAUDE.md, and a rule for one kind of work goes in the document or skill for that work. When you ask for that work, mention the document in your prompt and check in the panel that Claude opened it, since Claude does not always follow a line in CLAUDE.md that tells it to read a document.

Step 6

Write the working notes, CLAUDE.md

Claude Code reads a file called CLAUDE.md at the top of the folder at the start of every session. In it you tell Claude how to work in this folder. Have Claude write a first version with the prompt below, then check that it covers five things.

  1. Which document governs what. The specification governs style and pedagogy, the schedule governs the calendar, and so on.
  2. What each subfolder holds.
  3. How to compile the documents, such as LaTeX source into PDF, and where the output goes.
  4. The order of work for a new piece. Read the sources in the folder, check every computation, draft, read the prose against the specification, then compile the document and look at the output.
  5. That Claude proposes each change and waits for your approval before writing it.
Paste into the Claude panel

Read [course]_specification.md and look through this folder, then write a CLAUDE.md for this folder. It should say which document governs what, with the specification governing style and pedagogy, and what each subfolder holds. It should say how to compile the documents. It should give the order of work for a new piece, which is to read the sources in the folder, verify every number with a script before it enters a document, draft, check the prose against the specification, and compile the document and look at its pages. It should say that you propose each change and wait for my approval before writing it. Keep it under a page, and do not copy rules from the specification into it.

Keep it short. Claude reads the whole file at the start of every session. Anthropic’s documentation recommends keeping it under 200 lines, since everything Claude reads in a session shares its context window, the limited amount of text the model can take into account at once. A longer CLAUDE.md takes up more of that window and is followed less reliably. Two kinds of material tend to pile up in it over a quarter. Rules for one kind of work belong in the document for that work. A description of where each chapter stands goes stale as soon as you revise it, so keep it in the chapter file or in the dated handoff notes of Step 10.

Once you trust how Claude works, you can loosen the fifth item. In my folder, Claude now makes a change I asked for directly, after copying the file to an archive folder. Anything I did not ask for, it proposes first.

Step 7

Put the quarter in the folder

In backward design you start from what students will be assessed on and when, so put that in the folder as well. That means the syllabus, the schedule with its assessment dates, and for each assessment the standards or learning goals it covers, with sample questions if you publish them.

My course is graded by standards, and each standard is assessed at in-class sittings spread across the quarter. With the schedule and the standards in the folder, Claude plans from the assessment backward.

  • When it plans a lecture, it starts from where the last one stopped and from what the next sitting will ask.
  • When it drafts a sitting, it checks what the lectures covered in the lecture notes themselves, not in the plan. It also checks the earlier sittings, so that the new one asks something different.
  • Before it proposes cutting a question from the notes, it checks whether an assessment asks for the kind of task that question practices. That rule came from my correction when it once proposed cutting such a question.

After each class I tell Claude where the lecture stopped, and it records that.

Plans change during a quarter, so a note about the schedule goes out of date quickly. Mine includes a rule that such a note only records what was planned when it was written. Claude never treats it as a reason that something cannot happen. To find out what has been covered, Claude reads the current lecture notes and homework rather than the old plans.

Step 8

Let memory keep your corrections

Claude Code keeps a memory for each project, so that a correction you make in conversation is not lost when the session ends. When you correct it or settle a decision, it saves a short note as a markdown file. It also adds a one-line entry for the note to MEMORY.md, the index of memory notes. You can also tell it to remember something.

Between late September and November 13 my course project collected 134 notes. Ninety-three are corrections to how Claude works. Most of the rest record the state of the course, such as the decisions about each module, which questions each sitting used, and where each lecture stopped. A note gives the rule, the reason for it and how to apply it, and often quotes my words. The note below, shortened, records a correction about the fill-in blanks in my lecture notes.

Memory note, shortened 
---
name: blanks-for-key-ideas-only
description: A fill-in blank must ask for a key idea, never for algebra
type: feedback
---
He cut a blank that asked for a sum after the integrals in it cancel:
"it's just simplification. that should not be a question to ask this
audience." The blank for the factor 1/16, which drives the whole error
estimate, stays.

Why: the readers are third- and fourth-year mathematics majors. A blank
that only asks them to cancel terms is busywork, and it weakens the
blanks that do carry an idea.

How to apply: before placing a blank, ask whether the missing piece is an
idea the argument turns on, such as a factor, a hypothesis or the reason
a step works. If it is algebra the reader can do at a glance, write it in.

The lines between the two --- marks, the note’s frontmatter, give its name, a one-line description and its type. Claude uses the description to decide when the note is relevant.

A few more rules from my memory, shortened

  • “The length of the interval is halved at each step,” and not “Each step halves the length of the interval.” A sentence in which a machine, a method or a step does what only a person does reads as machine-written.
  • A section opens with the need it meets, stated in terms the reader already has, and does not describe the method until the questions have worked it out. An opening that summarizes a method the reader hasn’t met either gives the questions away or means nothing yet.
  • No sentence imagines what a student does or did. A hypothetical about cutting corners tells every reader they are suspected.
  • Sentences run at the length a mathematician would say them aloud, and every formula the argument turns on is displayed on a line of its own. Clipped short sentences read as machine-written.
  • A question asks students to “state the condition,” not to “name the condition.” “Name” asks for a label, and the point is the content.

Read what it saves. The notes are files you can open, so you can fix or delete a wrong note as soon as you see it. By default Claude keeps these notes in ~/.claude/projects/<project>/memory/, a hidden folder in your home directory. With one line in a settings file in the course folder, .claude/settings.json, you can move them into the course folder, where they show in the file list and sync to every computer you use.

Settings file 
{
  "autoMemoryDirectory": "~/path/to/course folder/claude_memory"
}

Have each note state the principle behind a correction rather than the single case. A note should say “no question may mention the theorem it tests,” and not “cut the phrase mean value theorem from the hint in question 3.” When a note records only the single case, rewrite it or ask Claude to.

Step 9

Watch for Goodhart’s law

Claude follows its notes eagerly, and a rule written for one situation tends to be applied to every situation that resembles it. I once gave Claude a sentence for introducing a result that follows a homework question. Later, every result in that chapter opened with the same sentence. Earlier, Claude had measured my own lecture notes and set target ranges for sentence length and pronoun use. It then revised a chapter until it fell inside nearly every range, and the chapter still read as if written for children.

Goodhart’s law

Claude treating a rule or a number as a target is, in my experience, the most common way this setup fails. Goodhart’s law, in Marilyn Strathern’s phrasing, says that “when a measure becomes a target, it ceases to be a good measure.” In both of my examples Claude met the target it had been given, the sentence or the ranges, and lost what the target was meant to achieve.

I keep this in check with three habits.

  • When you correct Claude, say whether the correction is for this one case or for every case like it. If Claude then applies it everywhere, tell it the correction was for one case, so that the note says so.
  • When a revision drops something you decided earlier in the same session, have Claude list your earlier instructions on that document and check the draft against the list before it shows you the next one.
  • When Claude keeps obeying the letter of a rule while missing its point, the rule is describing a symptom. Rewrite it to state the principle behind it.

Step 10

Turn routines into skills

A skill is a set of instructions for one job, kept in its own folder as a file called SKILL.md, along with any scripts the job needs. You start a skill by typing a slash and its name, as in /handoff. Claude can also start one on its own when the job matches the skill’s description, unless the skill is set to start only when you type its name. Once you have walked Claude through the same job three times, have it write a skill for that job with the prompt below.

Mine are these.

  • handoff. A conversation does not carry over to the next session, or to another computer. At the end of a session, /handoff saves to memory any rule I gave that is not there yet. It then writes a note saying what was done, which files changed, what is waiting on me and what to do next, and adds it to CURRENT.md, the index of handoff notes. At the start of the next session, on whichever of my three computers I am using, /handoff pickup reads the newest note and tells me where we stopped.
  • document-audit. Before a document goes to students, Claude uses it to read each sentence against my rules and to record that the audit was done.
  • no-fluff-response. By default, Claude spends my reading time on validation, summary and hedging. This skill sets how it writes to me while we work. It requires the first sentence to be the answer or the correction, and it bans openings that praise the question, closing offers of further help, and narration of what the model is about to do. In CLAUDE.md I ask Claude to apply it to every reply. You can download the packaged copy.
Paste into the Claude panel

Write a project skill for the job we just did, in .claude/skills/[name]/SKILL.md. Give the steps in order, the points where you stop and wait for my decision, and the files it reads and writes. Leave out anything that held only for this week.

Step 11

Work in sessions, and check everything

A session in my folder runs in the same order each time.

  1. I start with /handoff pickup, and Claude tells me where the last session stopped, what is waiting on me and what the note says to do next.
  2. I ask for one piece of work, such as the next two pages of a chapter. Claude reads the chapter, the memory notes that apply and the sources in the folder, and opens the longer documents that the work needs.
  3. Claude writes a short Python script for every computation, runs it, and keeps it in the folder, and only the checked values go into the document. My course folder has 137 of these scripts. That confirms the arithmetic, and I still judge whether the script computes the right thing.
  4. Claude copies the file to an archive folder and edits it.
  5. Claude reads each new sentence against my rules with the audit skill. Ask to see the audit itself, with a verdict on each sentence, since Claude can say it ran a check when it did not, and the panel shows whether it ran.
  6. Claude compiles the PDF, renders its pages as images and looks at them for figures that collide, answer spaces too small to write in, and bad page breaks.
  7. Claude lists every edit it made, quoting what it deleted, since a deletion is the one change you cannot see by reading the result. A report such as “Applied 13 replacements” gives you nothing to check.
  8. I review the compiled PDF and correct what is wrong, and Claude saves the corrections to memory.
  9. I end with /handoff.

Following the specification does not make the content correct. A model states a wrong claim as fluently as a right one, and when asked to mark what it is unsure of, it marks only the gaps it noticed. Because Claude works on your own files, the scripts, the page check and the audit are cheap enough to run every time. You still check the content and the logic yourself.

For a long job, such as reading about a hundred past exams and textbooks before drafting an assessment, have Claude start a progress file that lists what is done and what comes next, and update it after each step. Claude can stop partway through a long job when you reach the usage limit of your plan, and anything it had not saved to a file is lost.

Step 12

Consolidate at the end of the quarter

Over a quarter, memory fills with notes that repeat each other, notes about plans that have since changed, and rules that belong in a longer document. Claude also reads only the first 200 lines or 25 KB of MEMORY.md, so in a long index the last entries go unread.

When the quarter ends, have Claude sort the memory with the prompt below. Durable rules about how you teach go into the longer documents, where the next course and a colleague can use them, and the few that must hold in every session go into CLAUDE.md. Notes about this quarter’s course go to an archive. Duplicates are merged, and you settle the conflicts.

Paste into the Claude panel

Read every note in the memory folder, and CLAUDE.md. Sort the notes into three groups. The first holds durable rules about how I teach or write, the second holds facts about this quarter’s course, and the third holds notes that duplicate or contradict another note. For each durable rule, give the document it belongs in, the section and the text to add, and say whether that document already covers it. List the duplicates and contradictions in pairs and propose how to settle each. Write all of this to a dated memo, and do not edit the documents or the notes.

Read the memo line by line before you accept any of it. Moving a rule into a longer document is an edit you approve yourself.

In the same sitting, revise the longer documents yourself. Rewrite the purpose and audience for the next course. Condense the sections for kinds of material you aren’t using instead of deleting them. Reconcile rules that have changed, so that two versions of the same rule don’t both sit in the folder. And write down any design that didn’t work in class, since Claude will keep producing it until you say otherwise.

Review CLAUDE.md then too. It names the current course and its files, so it goes out of date sooner than the longer documents. Look for rules that belong in a longer document, for descriptions of a quarter that is over, and for anything Claude no longer needs to read at the start of every session.

Sort what you keep into three layers, so that you can revise one without disturbing the others.

  • Core. Principles that hold across everything you teach, such as the design principles, rejection triggers and voice. They go in the longer documents you carry to the next course.
  • Context. The course and the quarter, which you replace each time you teach it. They go in CLAUDE.md, the schedule and this quarter’s memory.
  • Conventions. One set for each kind of material, such as worksheets, exams and solution keys, with its format and its example piece. They go in a document or a skill for that kind of material.

Start the next course from the core and the conventions, and leave this quarter’s notes in the archive.
