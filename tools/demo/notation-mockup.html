What the two references say

Wikipedia, Pseudocode, "mathematical style pseudocode"

Its claim: in numerical computation, pseudocode is often mathematical notation from matrix and set theory mixed with the control structures of a programming language, and sometimes natural language as well. It gives the sum operator standing in for a whole loop, \(\text{return } \sum_{k \in S} x_k\), notes that non-ASCII typesetting (TeX, MathML) is normal for it, and records the older name, pidgin ALGOL.

That is the Mathematical option below. Two consequences to decide about, both visible in the puzzles once you switch to it. The good one: the slice line T[0..n−1, 0] ← y becomes a quantified assignment, which is the clearest that line gets in any of the five. The bad one: the same move lets a sum operator swallow a loop, and a block that swallows a loop removes exactly what the puzzle is testing. If we go this way, the rule has to be that \(\sum\) and \(\prod\) stay out of the blocks and live only in the brief.

Cornell CS482 handout (Naomi Nishimura, written for CS341)

It isn't a syntax specification. It's one page arguing about the level of detail, with seven guidelines and no example algorithms. Four of them bear on this decision, and two of them cut in opposite directions:

  1. "Mimic good code and good English", and specifically that variable names be mnemonic. That is an argument against the mathematical style's single letters, which is the cost flagged in its panel below.
  2. "Ignore unnecessary details. If you are worrying about the placement of commas, you are using too much detail [...] you shouldn't obsess about syntax." This is the one place our situation differs from hers. Her pseudocode is read and graded by a person, so syntax can stay loose; ours is parsed and executed, so it can't. What we can still do is pick the notation with the least syntax to learn, which is what the panel below is comparing.
  3. "Take advantage of programming shorthands", since if-then-else and loop structures are more concise than the English equivalent. An argument against Structured English.
  4. "Don't lose sight of the underlying model": it should be possible to see through the pseudocode to the model below. Against Structured English again, and the reason it is in this page only to mark the far end of the range.

Guideline 7 is "check for balance", which is the whole question here, so it doesn't settle it.
